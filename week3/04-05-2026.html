Core Concepts: Understanding Idempotency

What is Idempotency?

An operation is idempotent if performing it multiple times produces the same result as performing it once. In API design, this means:

  • User clicks "Upload" → File is uploaded once
  • User clicks "Upload" 3 times accidentally → File is still uploaded once
  • No duplicates, no data loss, consistent state
40 LPA Insight: Major companies like Amazon, Google, and Netflix ensure idempotency across all critical operations. When you understand this pattern, you're thinking like a senior architect.

Challenge 1: The Upload Problem

The Scenario

You have a file upload endpoint. A user uploads the same file 3 times:

  • Without idempotency: 3 copies on disk, wasted space, confusion
  • With idempotency: 1 copy on disk, linked to all 3 uploads, efficient

The Solution: Content Hashing

Instead of trusting the filename, generate a SHA-256 hash of the file content:

  • document.pdf (1MB) → Hash: a1b2c3...
  • contract.pdf (same content) → Hash: a1b2c3...
  • System recognizes duplicate and prevents re-upload

Stream-Based Hashing Strategy

const crypto = require('crypto');
const fs = require('fs');

// Create hash object
const hash = crypto.createHash('sha256');

// Stream processing (efficient for large files)
const fileStream = fs.createReadStream('large-file.bin');

fileStream.on('data', (chunk) => {
    // Update hash with each chunk (not stored in memory)
    hash.update(chunk);
});

fileStream.on('end', () => {
    // Get final hash
    const fileHash = hash.digest('hex');
    console.log('File fingerprint:', fileHash); // e.g., "a1b2c3d4e5f6..."

    // Now check database
    checkIfHashExists(fileHash);
});

Why Streaming Matters

Approach Memory Used For 1GB File For 20 Concurrent Users
Load Entire File 1GB per user 1GB RAM 20GB RAM (OOM!)
Streaming 64KB chunks 64KB RAM 1.2MB RAM (✓ Scalable)
Interview Question: "If you calculate the hash AFTER saving the file to disk, what happens if it's a duplicate?"

Answer: You'd have wasted disk space. The professional approach: write to a temporary location, calculate hash, check DB, then decide whether to keep or delete.

Challenge 2: Database Architecture

The Many-to-Many Relationship

Three-Table Design

To support efficient file deduplication at scale:

Table Primary Key Key Fields Purpose
users id (UUID) email, name, subscription User accounts
files id (UUID) hash (UNIQUE), storageKey, size Physical file metadata
user_files id (UUID) userId (FK), fileId (FK), fileName Links users to files
Why UNIQUE constraint on hash: The database prevents duplicate hashes at the storage level. Even if code has a bug, the database protects data integrity.

Smart Deletion Logic

The Challenge

User A and User B both have the same file. User A deletes it. What should happen?

  • Delete from user_files for User A only
  • Check: Any other users linked to this fileId?
  • If YES: Keep the physical file on S3
  • If NO: Delete from S3 AND files table

Reference Counting Implementation

async function deleteUserFile(userId, userFileId) {
    // Step 1: Remove link in user_files table
    await UserFile.deleteOne({ _id: userFileId, userId });

    // Step 2: Get the fileId
    const userFile = await UserFile.findById(userFileId);
    const { fileId } = userFile;

    // Step 3: Count remaining users with this file
    const remainingUsers = await UserFile.countDocuments({ fileId });

    // Step 4: If no users left, clean up
    if (remainingUsers === 0) {
        // Delete from database
        const fileData = await File.findByIdAndDelete(fileId);

        // Delete physical file from S3
        await s3.deleteObject({
            Bucket: 'my-bucket',
            Key: fileData.storageKey
        }).promise();
    }

    return { success: true, orphaned: remainingUsers === 0 };
}

The Failure Scenario

Interview Question: "What if the database delete succeeds but S3 deletion fails?"

Answer: That's why we use transactions. In MongoDB, we use atomic operations. In SQL, we use transaction blocks. The key: if ANY step fails, ALL steps rollback.

Challenge 3: HTTP Status Codes & REST Principles

Choosing the Right Status Code

Scenario Status Code Why? Response Body
File uploaded (new) 201 Created New resource created { status: "created", fileId: "..." }
File exists (duplicate) 200 OK Request succeeded, user's goal met { status: "existing", fileId: "..." }
Delete successful 204 No Content Success, but nothing to return (empty body)
File not found 404 Not Found Resource doesn't exist { error: "File not found" }
Validation failed 400 Bad Request Client sent invalid data { error: "Invalid hash format" }
UX Consideration: Sending 409 Conflict for a duplicate upload might make users think something went wrong. 200 OK with metadata in the response is better for UX while being technically correct.

Challenge 4: Choosing Your Database

Feature PostgreSQL (SQL) MongoDB (NoSQL)

Foreign Keys ✓ Enforced Manual validation

Senior Developer Wisdom: "Choose the database your team knows well. A well-implemented MongoDB system beats a poorly-implemented PostgreSQL system. But for Many-to-Many relationships with complex queries, SQL wins."

Common Mistakes to Avoid

Mistake 1: Not Handling Edge Cases

Problem: What if the file is 0 bytes? What if hash calculation fails?

Solution: Validate at every step. Empty files need special handling.

Mistake 2: Trusting the Client Hash

Problem: Browser sends hash, but user might be malicious.

Solution: Always recalculate on server. Use client hash as optimization hint only.

Mistake 3: Race Conditions

Problem: Two uploads with same hash arrive simultaneously.

Solution: Database UNIQUE constraint prevents duplicates atomically.

Interview Preparation

Common Questions

  • Q: "How would you detect file duplicates at scale?"
    A: Content hashing (SHA-256) + indexed database lookup. O(1) to check, not O(n).
  • Q: "What if someone uploads 1TB in 1KB chunks?"
    A: Streaming ensures constant memory usage, not linear scaling with file size.
  • Q: "How would you prevent race conditions?"
    A: UNIQUE constraints + database transactions ensure atomicity.
  • Q: "Why not store the filename as the UNIQUE key?"
    A: Users can name the same file differently. Content (hash) is the true unique identifier.
