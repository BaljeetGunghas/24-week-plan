Part 1: The Execution Context & Memory Allocation

Before any JavaScript code runs, the engine (V8, SpiderMonkey, JavaScriptCore) creates an Execution Context - the environment where code is evaluated. Think of it as a container that holds everything your code needs to execute.

The Two Major Memory Structures

Memory Layout in JavaScript Engine

1. The Call Stack

A highly structured, fast memory space for:

  • Primitive Types: Numbers, strings, booleans, symbols, undefined, null
  • Execution Contexts (Stack Frames): Each function call creates a frame
  • Pointers to Heap: Reference variables point to heap objects

2. The Memory Heap

A large, mostly unstructured region for:

  • Reference Types: Objects, arrays, functions
  • Dynamic Allocation: Size can change at runtime
  • Garbage Collection: Memory is reclaimed when unreachable

The Dual-Phase Lifecycle of Execution Context

Phase 1: Creation Phase

This is where the magic of hoisting happens:

  • Engine creates the window (browser) or global (Node.js) object
  • Sets up this binding
  • Hoists function declarations: Entire functions stored in heap, names added to scope
  • Hoists variable declarations: Names added to scope, values set to undefined
  • Creates scope chains and closure references

Phase 2: Execution Phase

Code runs line-by-line:

  • Assign values to variables
  • Execute function calls
  • Create new execution contexts for each function
  • Eventually pop contexts and reclaim memory

Hoisting Visualization

What you write: 
console.log(x);     // What is x here?
var x = 5;
console.log(x);     // What is x here?
getName();          // Will this work?

function getName() {
  return "Baljeet";
}
What the engine sees (Creation Phase): 
// Variables hoisted as undefined
var x = undefined;

// Function hoisted completely
function getName() {
  return "Baljeet";
}

// --- Now Execution Phase Begins ---
console.log(x);     // undefined (not an error!)
x = 5;              // Assignment happens here
console.log(x);     // 5
getName();          // Works perfectly! Already defined

Part 3: Stack Overflow & System Limits

The call stack has a fixed, finite size. When you exceed this limit, the engine throws a RangeError: Maximum call stack size exceeded.

What Causes Stack Overflow?

Infinite Recursion (The Most Common Culprit)

function recurse() {
  console.log("Recursing...");
  recurse();  // No base case! This will crash
}

recurse();
// Output: Uncaught RangeError: Maximum call stack size exceeded

Stack Limit by Browser

JavaScript Engine Browser/Runtime Approximate Limit Test Method
V8 Chrome, Edge, Node.js 10,000 - 15,000 frames Deep recursion test
SpiderMonkey Firefox 20,000 - 25,000 frames Slightly higher limit
JavaScriptCore Safari, iOS 8,000 - 12,000 frames More conservative
Chakra Older IE 5,000 - 10,000 frames Strict limits

Finding Your Stack Depth

JavaScript function to test stack depth: 
function getStackDepth() {
  let depth = 0;

  function recurse() {
    depth++;
    recurse();
  }

  try {
    recurse();
  } catch(e) {
    console.log(`Maximum stack depth: ${depth}`);
  }

  return depth;
}

const maxDepth = getStackDepth();
// Chrome: ~15,000
// Firefox: ~20,000
// Safari: ~10,000
// Node.js: ~12,000

Prevention & Optimization Strategies

Strategy 1 Convert Recursion to Iteration

❌ Recursive (Stack Overflow Risk): 
function factorial(n) {
  if (n <= 1) return 1;
  return n * factorial(n - 1);  // Deep stack for large n
}

factorial(10000);  // Stack overflow!
✓ Iterative (Safe): 
function factorial(n) {
  let result = 1;
  for (let i = 2; i <= n; i++) {
    result *= i;
  }
  return result;
}

factorial(10000);  // Works perfectly, O(1) space

Strategy 2 Tail Call Optimization (TCO)

In strict mode, some engines optimize tail calls (Chrome V8 doesn't, but SpiderMonkey does):

// Strict mode with tail call
'use strict';

function factorial(n, acc = 1) {
  if (n <= 1) return acc;
  return factorial(n - 1, n * acc);  // Tail call - can be optimized
}

// Note: V8 (Chrome) doesn't implement TCO yet, but this is valid in SpiderMonkey (Firefox)

Strategy 3 Use Trampoline Pattern

// Trampoline for safe recursion
function trampoline(fn) {
  let result = fn();
  while (typeof result === 'function') {
    result = result();
  }
  return result;
}

function factorial(n, acc = 1) {
  if (n <= 1) return acc;
  return () => factorial(n - 1, n * acc);  // Return function instead of calling
}

const result = trampoline(() => factorial(10000));  // Works safely!

Strategy 4 Batch Processing

Use setTimeout or setImmediate to let the call stack clear between iterations:

function processLargeArray(arr, batchSize = 1000) {
  let index = 0;

  function processBatch() {
    const end = Math.min(index + batchSize, arr.length);

    for (let i = index; i < end; i++) {
      // Process arr[i]
    }

    index = end;

    if (index < arr.length) {
      setTimeout(processBatch, 0);  // Let stack clear
    }
  }

  processBatch();
}

processLargeArray(new Array(1000000));

Part 5: Garbage Collection & Memory Leaks

How Garbage Collection Works

Modern JavaScript engines use sophisticated garbage collection algorithms to reclaim memory. The two main approaches are:

1. Mark-and-Sweep Algorithm

How It Works

  1. Mark Phase: Engine starts from root (global object) and marks all reachable objects
  2. Sweep Phase: Any unmarked objects are considered garbage and deallocated
  3. Compact Phase (Optional): Remaining objects are moved to fill gaps and improve cache locality

2. Generational Collection

V8's Generational Approach

  • Young Generation: Objects that are newly created, collected frequently (every few ms)
  • Old Generation: Objects that survived multiple GC cycles, collected less frequently
  • Insight: Most objects die young - this optimizes for the common case

Common Memory Leak Patterns

Leak 1: Forgotten Timers

function setupTimer() {
  const largeData = new Array(1000000);

  setInterval(() => {
    console.log(largeData.length);  // Timer keeps largeData alive
  }, 1000);

  // Never cleared! largeData leaks indefinitely
}

// ✓ Fix:
function setupTimerFixed() {
  const largeData = new Array(1000000);
  const timerId = setInterval(() => {
    console.log(largeData.length);
  }, 1000);

  // Later: clearInterval(timerId);
}

Leak 2: Forgotten Event Listeners

// ❌ Memory leak:
function attachListener() {
  const button = document.getElementById('myBtn');
  button.addEventListener('click', () => {
    console.log('Clicked!');
  });
  // Listener never removed!
}

// ✓ Fix:
function attachListenerFixed() {
  const button = document.getElementById('myBtn');
  const handler = () => console.log('Clicked!');

  button.addEventListener('click', handler);

  // Later: button.removeEventListener('click', handler);
}

Leak 3: Global Variables

// ❌ Accidental global variable:
function processData() {
  largeData = new Array(1000000);  // No 'let', 'const', or 'var' = global!
  // Now it's on window and never gets GC'd
}

// ✓ Fix:
function processDataFixed() {
  const largeData = new Array(1000000);  // Scoped, will be GC'd
}

Leak 4: Detached DOM Nodes

// ❌ DOM node leak:
const detachedDiv = document.querySelector('div');
const reference = detachedDiv;  // Keep reference
document.body.removeChild(detachedDiv);  // Remove from DOM
// But reference still exists! Node kept in memory

// ✓ Fix:
const div = document.querySelector('div');
// ... use it ...
document.body.removeChild(div);
div = null;  // Clear reference explicitly

Leak 5: Circular References

// ❌ Circular reference (old browsers):
function createCircular() {
  const obj1 = {};
  const obj2 = {};

  obj1.ref = obj2;
  obj2.ref = obj1;  // Circular!

  // Modern GC handles this, but be aware
}

// ✓ Best practice:
function createSafe() {
  const obj1 = { data: 'value' };
  // Don't create circular refs if avoidable
}

Part 6: The Temporal Dead Zone (TDZ)

This is a crucial concept often missed by junior developers but tested heavily in interviews.

What is TDZ?

The Temporal Dead Zone is the period between function entry and the point where a let or const variable is declared. During this period, the variable exists but is uninitialized and accessing it throws a ReferenceError.

function example() {
  console.log(x);  // ReferenceError: Cannot access 'x' before initialization

  let x = 5;  // ← TDZ ends here
}

// Why does this matter?
// 1. x is hoisted (engine knows it exists)
// 2. But it's not initialized to undefined
// 3. Accessing it before declaration = error, not undefined!

// Compare with var:
function exampleVar() {
  console.log(y);  // undefined (hoisted and initialized)
  var y = 5;
}

// var is initialized to undefined during creation phase
// let/const are not initialized until the declaration statement executes

TDZ in Different Scenarios

Scenario 1: Block Scope TDZ

let x = 'global';

{
  console.log(x);  // ReferenceError! TDZ for block-scoped x
  let x = 'block';
}

// Engine knows x will be declared in this block,
// so the global x is shadowed from the start of the block

Scenario 2: TDZ in Closures

function outer() {
  console.log(x);  // ReferenceError! x is in closure's TDZ

  function inner() {
    let x = 5;
  }
}

// The inner x is hoisted in inner's scope,
// but accessing it from outer during its TDZ is an error

Scenario 3: TDZ with Default Parameters

function func(a = b, b = 2) {
  console.log(a, b);
}

func();  // ReferenceError! b is in TDZ when a's default is evaluated

// Parameters are processed left to right
// When a's default (which references b) is evaluated, b is not yet initialized

Part 7: Interview Mastery - Top 10 Questions

Question 1: Explain the difference between stack and heap memory

Answer: The stack stores primitive values and execution contexts in LIFO order. It's fast, automatic, and fixed-size. The heap stores reference types (objects, arrays) in a dynamic, unordered manner. Stack is per-thread and local; heap is global and shared. When you assign a primitive, you copy the value. When you assign an object, you copy the reference (pointer).

What they're testing: Understanding of memory models, scoping, and how JavaScript engines work.

Question 2: What causes a stack overflow?

Answer: Stack overflow occurs when the call stack exceeds its maximum size, typically 10,000-20,000 frames depending on the engine. The most common cause is infinite recursion without a base case. Each function call pushes a new frame onto the stack; if these frames never pop, you hit the limit.

Prevention: Convert recursion to iteration, use the trampoline pattern, or batch process with setTimeout to let the stack clear.

What they're testing: Deep understanding of call stack mechanics and optimization techniques.

Question 3: How does hoisting work?

Answer: During the creation phase of execution context, the engine scans the code and:

  • Hoists function declarations completely (name + body)
  • Hoists variable declarations but initializes them to undefined
  • Does NOT hoist assignments or function expressions

Key insight: Hoisting is not moving code around; it's about the creation phase happening before the execution phase.

What they're testing: Understanding of the two-phase execution model.

Question 4: What is the temporal dead zone?

Answer: The temporal dead zone (TDZ) is the period between a block's entry and the point where a let or const variable is declared. During TDZ, the variable is hoisted but uninitialized. Accessing it throws a ReferenceError, not undefined.

Why it matters: let and const are not initialized to undefined like var. The TDZ prevents accidental use before declaration.

What they're testing: Distinction between var, let, and const hoisting behavior.

Question 5: Can you identify a memory leak in this code?

Common leaks:

  • Event listeners never removed
  • Timers/intervals never cleared
  • Global variable references to large objects
  • Circular references (in old browsers)
  • Detached DOM nodes still referenced

Detection: Use Chrome DevTools Memory tab → Take heap snapshot → Compare snapshots over time → Look for growing object counts.

What they're testing: Practical debugging skills and knowledge of common patterns.

Question 6: What is a closure and how does it affect memory?

Answer: A closure is a function that retains references to variables from its outer scope even after the outer function returns. The lexical environment (scope) is kept alive in the heap.

Memory implication: Closures keep their parent scope alive. If you create many closures with heavy outer scopes, you can cause memory bloat.

function createClosures() {
  const largeArray = new Array(1000000);
  const closures = [];

  for (let i = 0; i < 1000; i++) {
    closures.push(() => largeArray[i]);  // Each closure captures largeArray!
  }

  return closures;  // All 1000 closures keep largeArray alive
}

What they're testing: Understanding of closures, scope chains, and memory management.

Question 7: What is the call stack and how is it used in debugging?

Answer: The call stack is a LIFO data structure that tracks function calls. When a function is called, a frame is pushed; when it returns, the frame is popped.

Debugging: Error stack traces show the call stack at the moment of error. Reading a stack trace tells you:

  • The exact function where the error occurred
  • The chain of calls that led to that function
  • The file name and line number for each call

What they're testing: Practical debugging skills and call stack understanding.

Question 8: How do primitives and reference types differ in memory?

Primitives (Stack): Values are stored directly on the stack. Assignment copies the value.

References (Heap): Values are stored on the heap; pointers are on the stack. Assignment copies the pointer.

let a = 5;
let b = a;
b = 10;
console.log(a);  // 5 (unchanged)

let obj1 = {val: 5};
let obj2 = obj1;
obj2.val = 10;
console.log(obj1.val);  // 10 (changed!)

What they're testing: Deep understanding of data types and memory models.

Question 9: Explain how garbage collection works in JavaScript

Algorithm: Modern engines use mark-and-sweep with generational collection.

  1. Mark Phase: Start from root (global object), mark all reachable objects
  2. Sweep Phase: Unreachable (unmarked) objects are deallocated
  3. Compact Phase: Move objects to fill gaps, improve cache locality

Generational: V8 splits objects into young and old generations. Young generation is collected frequently (most objects die young), old generation less frequently.

What they're testing: Knowledge of GC algorithms and memory management strategies.

Question 10: How would you optimize this recursive function to prevent stack overflow?

Approach 1: Convert to iteration

// Recursive
function sum(arr, i = 0) {
  return i === arr.length ? 0 : arr[i] + sum(arr, i + 1);
}

// Iterative (O(1) space, no stack overflow)
function sumIterative(arr) {
  let total = 0;
  for (let i = 0; i < arr.length; i++) {
    total += arr[i];
  }
  return total;
}

Approach 2: Use trampoline pattern

Approach 3: Batch with setTimeout

Part 9: JavaScript Engine Implementation Details

V8 Engine (Chrome, Node.js)

Key Characteristics

  • JIT Compilation: Compiles hot code to machine code for speed
  • Generational GC: Young generation collected frequently, old generation rarely
  • No TCO: Tail call optimization not implemented (doesn't optimize tail calls)
  • Stack Limit: ~10,000-15,000 frames
  • Internals: Hidden classes for object layout, inline caching for method calls

SpiderMonkey Engine (Firefox)

Key Characteristics

  • JIT Compilation: IonMonkey compiler for optimization
  • Generational GC: Similar to V8 but with different thresholds
  • TCO Support: Tail call optimization IS implemented in strict mode
  • Stack Limit: ~20,000-25,000 frames (higher than V8)
  • Known for: More memory efficient, good for Firefox

JavaScriptCore (Safari, iOS)

Key Characteristics

  • LLVM Backend: Uses LLVM for code generation
  • Generational GC: Markable/Eden pattern
  • Stack Limit: ~8,000-12,000 frames (more conservative)
  • Known for: Energy efficiency on mobile devices

Challenge 1: Find the Memory Leak

Code with Memory Leak

class DataProcessor {
  constructor() {
    this.cache = [];
  }

  processData(data) {
    const processed = data.map(x => x * 2);
    this.cache.push({ data: processed, time: new Date() });

    document.getElementById('btn').addEventListener('click', () => {
      console.log(this.cache);
    });
  }
}

const processor = new DataProcessor();
for (let i = 0; i < 1000; i++) {
  processor.processData([1, 2, 3, 4, 5]);
}

Identify the Issues

Issue 1: Event listener added 1000 times but never removed - each listener keeps the processor in memory

Issue 2: Cache grows indefinitely without clearing old entries

Issue 3: Each Date object adds unnecessary memory

Memory impact: ~1000 listeners × processor reference = massive leak

Fixed Version

class DataProcessor {
  constructor() {
    this.cache = [];
    this.maxCacheSize = 100;  // Limit cache
    this.clickHandler = () => console.log(this.cache);
  }

  processData(data) {
    const processed = data.map(x => x * 2);

    // Limit cache size
    this.cache.push({ data: processed });
    if (this.cache.length > this.maxCacheSize) {
      this.cache.shift();  // Remove oldest
    }
  }

  setupListeners() {
    const btn = document.getElementById('btn');
    btn.addEventListener('click', this.clickHandler);
  }

  cleanup() {
    const btn = document.getElementById('btn');
    btn.removeEventListener('click', this.clickHandler);
  }
}

const processor = new DataProcessor();
processor.setupListeners();

// Later: processor.cleanup();

Challenge 2: Prevent Stack Overflow

Problematic Recursive Code

// This will overflow for large arrays
function sumRecursive(arr, i = 0) {
  if (i === arr.length) return 0;
  return arr[i] + sumRecursive(arr, i + 1);
}

sumRecursive(new Array(100000).fill(1));  // Stack overflow!

Solution 1: Iterative

function sumIterative(arr) {
  let total = 0;
  for (let i = 0; i < arr.length; i++) {
    total += arr[i];
  }
  return total;
}

sumIterative(new Array(100000).fill(1));  // Works!

Solution 2: Trampoline Pattern

function trampoline(fn) {
  let result = fn();
  while (typeof result === 'function') {
    result = result();
  }
  return result;
}

function sumTrampoline(arr, i = 0, acc = 0) {
  if (i === arr.length) return acc;
  return () => sumTrampoline(arr, i + 1, acc + arr[i]);
}

const result = trampoline(() => sumTrampoline(new Array(100000).fill(1)));
console.log(result);  // Works safely!

Challenge 3: Memory Efficient Data Structure

Create an Object Pool to Reduce GC Pressure

// Object Pool Pattern - reuse objects instead of creating new ones
class ObjectPool {
  constructor(ObjectClass, initialSize = 10) {
    this.ObjectClass = ObjectClass;
    this.available = [];
    this.inUse = new Set();

    for (let i = 0; i < initialSize; i++) {
      this.available.push(new ObjectClass());
    }
  }

  acquire() {
    let obj;
    if (this.available.length > 0) {
      obj = this.available.pop();
    } else {
      obj = new this.ObjectClass();  // Create if pool empty
    }
    this.inUse.add(obj);
    return obj;
  }

  release(obj) {
    if (this.inUse.has(obj)) {
      this.inUse.delete(obj);
      obj.reset?.();  // Optional reset method
      this.available.push(obj);
    }
  }
}

// Usage:
class Point {
  constructor() {
    this.x = 0;
    this.y = 0;
  }
  reset() {
    this.x = 0;
    this.y = 0;
  }
}

const pool = new ObjectPool(Point, 100);

// Reuse instead of creating:
for (let i = 0; i < 10000; i++) {
  const point = pool.acquire();
  point.x = i;
  point.y = i * 2;

  // Use point...

  pool.release(point);  // Return for reuse
}

Learning Summary & Key Takeaways

Execution Context

Two phases: creation (hoisting) and execution. Understanding this explains most "weird" JavaScript behavior.

Memory Models

Stack for primitives (fast, automatic), heap for objects (dynamic, GC'd). This fundamental distinction underpins all memory behavior.

Call Stack

LIFO data structure for function calls. Understanding this is essential for debugging and preventing stack overflow.

System Limits

Know your engine's stack limit (V8: ~15K, Firefox: ~25K). Convert recursion to iteration when needed.

Garbage Collection

Mark-and-sweep with generational collection. Knowledge of GC helps you write memory-efficient code and debug leaks.

Practical Debugging

Use Chrome DevTools Memory tab for heap snapshots and allocation timelines. Profiling is your best friend.

  • Execution Context Phases: Creation phase does hoisting, execution phase runs code
  • Hoisting Rules: Functions fully hoisted, vars hoisted as undefined, let/const in TDZ
