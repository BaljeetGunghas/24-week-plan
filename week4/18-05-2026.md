## 🧠 Part 1: The Execution Context & Memory Allocation

Before code runs, the JavaScript engine (like V8) creates an **Execution Context**. Think of this as the environment or container where your code is evaluated and executed.

There are two major memory structures inside this context:

1. **The Memory Heap:** A large, mostly unstructured region of memory used for **Reference Types** (Objects, Arrays, Functions). Memory allocation here is dynamic because the size can change.
2. **The Call Stack:** A highly structured, fast memory space used for **Primitive Types** (Strings, Numbers, Booleans) and **Execution Contexts (Stack Frames)**.

### **The Dual-Phase Lifecycle**

Every execution context goes through two distinct phases:

1. **Creation Phase:** The engine sets up the `window` or `global` object, creates the `this` binding, and sets up memory space for variables and functions (**Hoisting**). Variables are initialized as `undefined`, and functions are stored entirely in the heap.
2. **Execution Phase:** The engine reads your code line-by-line, assigns values to variables, and executes functions.

---

## 🥞 Part 2: The JavaScript Call Stack Visualization

The JavaScript Engine runs on a **Single Thread**, meaning it can only do one thing at a time. To manage the execution of multiple functions, it uses a **Call Stack**.

The Call Stack strictly follows the **LIFO (Last In, First Out)** principle:

* When a function is called, a new **Stack Frame** (Execution Context) is created and **pushed** onto the top of the stack.
* When a function finishes executing, its frame is **popped** off the stack, and memory is reclaimed.


## ⚠️ Part 3: JS Engine Call Stack Limits (Stack Overflow)

Because memory allocation on the Call Stack is synchronous and fixed, it has a strict size limit. If you keep pushing contexts onto the stack without popping them off, you hit a **Stack Overflow** error.

This most commonly happens with infinite or un-optimized recursion:

```javascript
function recurse() {
  recurse(); // No base case to terminate execution
}
recurse(); 
// Uncaught RangeError: Maximum call stack size exceeded

```

*Note: In modern browsers like Chrome (V8), the maximum call stack limit is usually around 10,000 to 11,000 concurrent frames before it safeguards the system and crashes.*

### 📋 The Core Logic: Why a Stack?

When parsing brackets, nested expressions must close in the reverse order of how they were opened. This perfectly matches the **Last In, First Out (LIFO)** nature of a Stack.

* Every time you encounter an **opening bracket** (`(`, `[`, `{`), you push it onto the stack (delaying its resolution).
* Every time you encounter a **closing bracket** (`)`, `]`, `}`), it must match the *most recently opened* bracket. That means you pop the top item off the stack and check for a match.
* If the stack is empty when a closing bracket appears, or if the popped bracket doesn’t match, the string is instantly invalid.
* At the end of the string, the stack **must be completely empty**. If anything is left over, an opening bracket was left unclosed.

---

### 💻 35 LPA Standard Implementation (JavaScript)

Let's write this cleanly using an object map for $O(1)$ lookups instead of ugly `if/else` clusters, and add an early exit constraint check.

```javascript
/**
 * @param {string} s
 * @return {boolean}
 */
const isValid = (s) => {
    // Edge case / Early Exit: Odd length strings can NEVER be valid
    if (s.length % 2 !== 0) return false;

    const stack = [];
    
    // Hash map for O(1) matching configuration
    const bracketMap = {
        ')': '(',
        ']': '[',
        '}': '{'
    };

    for (let i = 0; i < s.length; i++) {
        const char = s[i];

        // If it is a closing bracket
        if (bracketMap[char] !== undefined) {
            // Pop the top element from stack (returns undefined if empty)
            const topElement = stack.pop();
            
            // If the popped element doesn't match the required opening bracket
            if (topElement !== bracketMap[char]) {
                return false;
            }
        } else {
            // It's an opening bracket, push it onto the stack
            stack.push(char);
        }
    }

    // If stack is completely empty, all brackets were matched perfectly
    return stack.length === 0;
};

```

---

### 📊 Complexity Analysis

* **Time Complexity:** $O(N)$ because we traverse the string of length $N$ exactly once. Each push and pop operation takes $O(1)$ time.
* **Space Complexity:** $O(N)$ in the absolute worst-case scenario where the string consists entirely of opening brackets (e.g., `((((((`), meaning we push every single character onto the stack.

---

### 🔍 Crucial Edge Cases to Explain to an Interviewer

1. **`"["` (Single character / Leftover elements):** The loop finishes, but `stack.length === 0` evaluates to `false` because `[` is still trapped inside.
2. **`"]"` (Starting with a closing element):** The loop checks `bracketMap[']'`, calls `stack.pop()` on an empty array which returns `undefined`. `undefined !== '['` evaluates to true, triggering an immediate `false` return.
3. **`"([)]"` (Wrong closure order):** The stack receives `(`, then `[`. When `)` arrives, it pops `[` off the top. Since `[` does not match `(`, it safely fails.

### 🔍 Spot the Bug in your Brute Force

Look closely at this line:

```javascript
while (arr[right] <= arr[i] && right < arr.length)

```

**The Issue:** If `right` increments until it equals `arr.length`, the condition `arr[right] <= arr[i]` evaluates to `undefined <= arr[i]`, which is `false`. The loop terminates, which is fine, but in languages other than JavaScript (or if you don't check carefully), checking an index out of bounds first can cause a crash. More importantly, order matters in conditional expressions due to **short-circuit evaluation**.

If you write `right < arr.length` *first*, JavaScript will stop checking immediately if it's out of bounds:

```javascript
while (right < arr.length && arr[right] <= arr[i])

```

### 💡 Moving Toward the Optimization: The Core Flaw of Brute Force

Let's look at what brute force is forgetting.

Imagine you have a decreasing sequence: `[75, 71, 69, 72]`

* Your code sits at `75`, looks at `71`, looks at `69`, looks at `72`. It realizes `72` isn't bigger than `75`, so it keeps going.
* Then, the outer loop moves to `71`. Your code sits at `71`, looks at `69`, and looks at `72`. It says "Ah! `72` is bigger than `71`!" and stops.

**Notice the waste?** When you were standing at `75`, you *already looked* at `71` and `69` and `72`. You already had the information that `72` is warmer than `71` and `69`, but because the outer loop reset your tracking, you threw that information away and scanned them all over again.

### 🛠️ The Monotonic Stack Intuition

To avoid re-scanning, we need a way to "remember" the days we haven't found a warmer temperature for yet.

Imagine a line of people waiting to see a warmer day.
If today is **colder** than the person before us, we just join the line and wait.
If today is **warmer** than the person at the front of the line, that person can finally leave the line! We calculate their wait time, give them their answer, and then we check the next person in line.

Because we keep waiting if it's colder, the line will naturally stay sorted in a **decreasing** order. This is called a **Monotonic Decreasing Stack**.

Instead of storing the temperature numbers in the stack, we store the **indices** of the days. Why? Because if we have the index, we can always look up the temperature *and* calculate the distance between days ($currentIndex - storedIndex$).

# Introduction to Monotonic Stack

A monotonic stack is a special type of stack data structure where elements are kept in either increasing or decreasing order. The main idea is to maintain this order while pushing and popping elements, which helps solve a wide range of problems efficiently.

## Understanding Monotonic Stack
A monotonic stack is a stack that maintains its elements in a fixed order either increasing or decreasing.

When a new element is pushed, it is compared with the top of the stack. If the order is violated, elements are popped until the property is restored, and then the new element is pushed.

This way, the stack always stays ordered, and since each element is pushed and popped at most once, the overall operations run in linear time.

### Types of Monotonic Stack:
Monotonic Stacks can be broadly classified into two types:

Monotonic Increasing Stack
Monotonic Decreasing Stack

#### Monotonic Increasing Stack
Elements inside the stack are always in increasing order.
While inserting a new element, all greater elements are popped.
Example:

For arr[] = [1, 7, 9, 5]:

Push 1 → [1]
Push 7 → [1, 7] (since 7 > 1, order holds)
Push 9 → [1, 7, 9] (since 9 > 7, order holds)
Push 5 → pop 9, pop 7, then push 5 → [1, 5]
Here we can see that at every step, the stack maintains an increasing order from bottom to top.


#### Monotonic Decreasing Stack
Elements inside the stack are always in decreasing order.
While inserting a new element, all smaller elements are popped.
Example:

For arr[] = [1, 7, 9, 5]:

Push 1 → [1]
Push 7 → pop 1, then push 7 → [7]
Push 9 → pop 7, then push 9 → [9]
Push 5 → [9, 5] (since 5 < 9, order holds)
 Here we can see that at every step, the stack maintains a decreasing order from bottom to top.

---------------------------------------------------------------


A monotonic stack is a specialized stack that maintains its elements in a strictly sorted order (either entirely increasing or decreasing). It eliminates the need for nested $O(n^2)$ loops in array problems by allowing you to process sequences in a single, linear $O(n)$ pass. [1, 2, 3]  
The core intuition for a monotonic stack revolves around "keeping track of un-shadowed candidates" as you move forward in an array. It is perfectly suited for questions that ask you to find the next greater or next smaller element in a sequence. [2, 4, 5]  
The Two Core Variations 
Depending on what you are trying to find, you will use one of two main rules: 
1. Monotonic Decreasing Stack (Used for "Next Greater") • Rule: Before pushing a new number, pop all elements from the stack that are smaller than the new number. 
• Intuition: The new, larger number has just "shadowed" or overtaken those smaller numbers. You no longer need to keep the smaller numbers around as future "greater" elements, so you pop them and map their answers to the new number. 
• Stack State: Elements are strictly decreasing from bottom to top. [4, 6, 7]  

2. Monotonic Increasing Stack (Used for "Next Smaller") • Rule: Before pushing a new number, pop all elements from the stack that are larger than the new number. 
• Intuition: The new, smaller number is now the dominant, smaller element in the sequence. It overtakes the larger elements that came before it. 
• Stack State: Elements are strictly increasing from bottom to top. [2, 4, 6, 7, 8]  

Why It Takes $O(n)$ Time 
Even though you are popping and pushing within loops, the overall runtime remains $O(n)$ because every element is pushed onto the stack exactly once and popped at most once. [1]
