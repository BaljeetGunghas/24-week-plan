Section 2: Deep Code Analysis

2.1 Initialization & Server Setup

const server = http.createServer((req, res) => {
  if (req.method === "POST") {
    const busboy = Busboy({ headers: req.headers });
    // ... handling logic
  }
});

What's Happening:

  • http.createServer() creates a native Node.js server (no framework overhead)
  • Busboy({ headers: req.headers }) initializes parser with request headers
  • Busboy automatically detects multipart boundary and content types from headers

2.2 File Event & Streaming

busboy.on("file", (name, file, info) => {
  const { filename, mimeType } = info;
  const saveTo = path.join(__dirname, "uploads", filename);

  const writeStream = fs.createWriteStream(saveTo);
  file.pipe(writeStream);
});

Key Concepts:

  • Readable Stream: file is a readable stream from Busboy
  • Writable Stream: writeStream writes to disk
  • Pipe: Connects readable to writable, data flows automatically
  • Backpressure: Node.js automatically pauses reading if disk is slow

2.3 Validation & Error Handling

const allowedTypes = [
  "image/jpeg", "image/png", "application/pdf",
  "text/plain", "video/mp4"
];

if (!allowedTypes.includes(mimeType)) {
  file.resume(); // Consume stream without saving
  if (!res.writableEnded) {
    res.writeHead(400);
    res.end(`Error: ${mimeType} not supported`);
  }
  return;
}

Critical Learning Points:

  • WHY file.resume()? If you don't consume a stream, it stays paused forever, connection hangs
  • WHY res.writableEnded check? Prevents ERR_HTTP_HEADERS_SENT if multiple files upload
  • MIME Type Validation: Checks actual file type, not just extension

2.4 Cleanup Logic (Request Abort Handling)

req.on("aborted", () => {
  if (!isUploadComplete) {
    writeStream.destroy();
    fs.unlink(saveTo, (err) => {
      if (!err) console.log(`Deleted: ${filename}`);
    });
  }
});

Why This Is Critical:

  • User closes browser mid-upload → request aborts
  • Without cleanup → partial file stays on disk
  • writeStream.destroy() closes the file handle
  • fs.unlink() removes incomplete file

2.5 The Finish Event

busboy.on("finish", () => {
  res.writeHead(200, { Connection: "close" });
  res.end("Upload successful!");
});

Timing: This fires AFTER all files finish uploading and all fields are parsed.

Section 3: Stream & Backpressure Fundamentals

3.1 What Is Backpressure?

Analogy: Imagine a fire hydrant (readable source) and a bucket (writable destination).

  • Without Backpressure: Hydrant blasts at max → bucket overflows → water everywhere (RAM fills)
  • With Backpressure: If bucket is full, hydrant automatically slows down

In Code: file.pipe(writeStream) handles backpressure automatically:

// What happens internally:
if (!writeStream.write(chunk)) {
  // Disk is slow, pause reading
  file.pause();
}

writeStream.on('drain', () => {
  // Disk caught up, resume reading
  file.resume();
});

3.2 Why Not Buffer Everything?

// BAD: Loads entire file into memory
const data = await req.body; // 700MB file = 700MB RAM!

// GOOD: Stream approach
file.pipe(writeStream); // Only 4MB RAM regardless of file size!

3.3 Backpressure in Production

Memory Profile:

Approach File Size Memory Used Max Concurrent
Buffer (fs.writeFile) 1GB 1GB 10 users (10GB RAM)
Stream (file.pipe) 1GB 4MB 1000+ users (4GB RAM)

Section 5: 50+ Interview Questions

BEGINNER LEVEL (5 Questions)

Beginner Q1: What is Busboy and why do we use it?

WHAT: Busboy is a Node.js module that parses multipart/form-data streams (file uploads).

WHY: Raw HTTP requests send files as binary streams. Busboy separates file data from form fields and emits events as data arrives.

HOW: It listens to the request stream and fires "file" and "field" events as it encounters them in the multipart message.

Beginner Q2: What does file.pipe(writeStream) do?

WHAT: Pipe connects a readable stream to a writable stream, automatically flowing data from one to the other.

WHY: Handles backpressure automatically - if the disk is slow, reading pauses; when disk catches up, reading resumes.

HOW: Node.js internally uses a highWaterMark (default 16KB) to buffer data. When buffer fills, it signals pause to the readable stream.

Beginner Q3: Why do we call file.resume() on invalid uploads?

WHAT: file.resume() tells Node.js to consume the stream without saving it (discards data).

WHY: If you don't consume a paused stream, Node.js waits forever for someone to read it. The connection hangs, socket stays open, server resources leak.

HOW: Calling resume() on a rejected file immediately drains all incoming bytes into the void, freeing up resources.

Beginner Q4: What does res.writableEnded check?

WHAT: Checks if the HTTP response has already been sent to the client.

WHY: If you try to call res.writeHead() or res.end() twice, Node.js throws ERR_HTTP_HEADERS_SENT and crashes.

HOW: In multipart uploads with multiple files, if the first file is rejected, we send an error response. When Busboy processes the second file, we must check if response already sent before sending again.

Beginner Q5: What is the difference between streaming and buffering?

STREAMING: Process data as it arrives, small chunks at a time (constant memory).

BUFFERING: Load entire file into memory before processing (memory = file size).

EXAMPLE: 1GB file - streaming uses 4MB RAM, buffering uses 1GB RAM.

INTERMEDIATE LEVEL (15 Questions)

Intermediate Q6: Walk me through the complete upload flow from client to disk

FLOW:

  1. Client sends POST request with multipart/form-data containing file
  2. req.pipe(busboy) - Node.js pipes incoming HTTP data to Busboy
  3. Busboy parses multipart boundary, emits "file" event
  4. Event handler validates MIME type
  5. If valid: file.pipe(writeStream) - data flows to disk
  6. If invalid: file.resume() - data discarded
  7. writeStream emits "finish" when done
  8. All files done → busboy emits "finish" → res.end()
Intermediate Q7: Explain backpressure and how pipe() handles it

BACKPRESSURE: When data source is faster than destination, buffer fills up.

PIPE HANDLING:

  • writeStream.write(chunk) returns true if buffer has space
  • If it returns false → pipe automatically calls file.pause()
  • When writeStream drains → 'drain' event fires → pipe calls file.resume()

RESULT: Memory stays constant, no overflow.

Intermediate Q8: What happens if a user closes their browser mid-upload?

WITHOUT CLEANUP: Partial file remains on disk, wasting storage.

WITH CLEANUP (our code):

  • Browser close triggers 'aborted' event on req
  • req.on('aborted', ...) listener fires
  • If upload not complete: writeStream.destroy() stops writing
  • fs.unlink() removes partial file

RESULT: Clean disk state, no orphaned files.

Intermediate Q9: How does the code prevent ERR_HTTP_HEADERS_SENT?

PROBLEM: If first file is invalid, we send 400 response. Then Busboy processes second file and tries to send response again → crash.

SOLUTION:

if (!res.writableEnded) {
  res.writeHead(400);
  res.end(`Error: ...`);
}

Check if response already sent before trying to send it.

Intermediate Q10: What is highWaterMark and why does it matter?

WHAT: Default buffer size before backpressure triggers (default 16KB for readable, 16KB for writable).

WHY: Too small → too many pause/resume events; too large → memory spike.

TUNING: For file uploads, can increase to 64KB or 256KB for better throughput.

Intermediate Q11: How would you handle multiple file uploads in one request?

CURRENT: Busboy fires multiple "file" events, one per file.

HANDLING: Each file event gets its own writeStream, validation, and cleanup listener.

CHALLENGE: Must not send response until ALL files done → that's why busboy.on('finish') exists.

  • Lower memory footprint

Advanced Q27: Explain backpressure handling in depth

SCENARIO: 100Mbps internet, 50Mbps disk write.

WITHOUT BACKPRESSURE:

  • Network buffer fills with 50Mbps of unwritten data
  • Server RAM fills to 500MB, 1GB, crashes

WITH BACKPRESSURE (our code):

  • writeStream buffer fills
  • file.pipe() detects write() returned false
  • Calls file.pause() → network read pauses
  • When disk catches up, writeStream emits 'drain'
  • pipe() calls file.resume() → network read resumes
  • Memory stays constant at ~4MB

});

Expert Q41: Explain the CAP theorem in context of distributed file uploads

CAP THEOREM: Can't have all three of: Consistency, Availability, Partition tolerance.

FOR FILE UPLOADS:

  • Consistency: All replicas see same file version (slow, strong consistency)
  • Availability: Upload always succeeds (fast, eventual consistency)
  • Partition Tolerance: System works if network partitions

CHOICE: Most systems pick AP (Availability + Partition). Allow temporary inconsistency, resolve later.

  • Network Isolation: Separate VPC per tenant (AWS)

VERIFICATION: Tenant A cannot read Tenant B's files via path traversal, permission elevation, or key reuse.

Expert Q50: Compare QUIC vs TCP for file uploads

TCP: Industry standard, 50+ years mature.

  • 3-way handshake overhead
  • Head-of-line blocking (one lost packet blocks all)
  • Proven, widely supported

QUIC (HTTP/3): Modern, Google-developed.

  • 0-RTT connection reuse
  • Multiplexing without head-of-line blocking
  • Connection migration (mobile users)
  • 5-10% faster uploads in poor networks

RECOMMENDATION: QUIC for mobile/IoT, TCP for stability.
